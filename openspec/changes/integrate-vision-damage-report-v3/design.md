## Context

主线当前使用 `damage-report.v1`：报告请求包含像素面积、裂缝几何和规则筛查等级，远程模型返回完整持久化对象，报告生成后直接进入后续阶段。独立优化模块证明了视觉模型直接查看原图和识别覆盖图、仅使用最小检测线索、提供人工编辑确认的可行性，但该模块基于旧工程快照，使用旧知识库入口和不同的流式回调语义，并且仍允许模型控制证据项集合与部分审计字段。

当前主线已经具备 active-v2 RAG、层级证据、来源模式、检索告警和“累计全文”流式预览。这些能力是上游稳定契约，报告 v3 必须增量接入，不能用优化目录整体覆盖。

## Goals / Non-Goals

**Goals:**

- 建立只含最小定位线索和视觉附件的报告 v3 输入契约。
- 将 AI 业务草稿与本地系统审计、人工复核状态分离。
- 在单次和分块生成路径上强制完整、唯一、稳定的证据对应。
- 提供受预算约束、去元数据并可审计的视觉附件编码。
- 增加 GUI 人工编辑、实名确认和施工方案门控。
- 保留主线 active-v2 RAG、GenerationContext 扩展字段及累计式流式预览。
- 让修复计划、施工方案、Markdown、DOCX 和清单消费同一 v3 报告事实。

**Non-Goals:**

- 不更换 YOLO 模型、不重做检测或训练流程。
- 不把视觉模型输出升级为结构安全鉴定、设计结论或施工指令。
- 不恢复像素面积、裂缝宽度或面积比例的自动等级规则。
- 不改造 active-v2 RAG 的索引、检索、语义模型或生产激活机制。
- 不在本变更中制作新的冻结发布包。

## Decisions

### 1. AI 草稿与持久化报告分离

新增 `DamageReportDraft`，只包含 subject、摘要、总体辅助等级、理由、损伤明细和局限性。远程 JSON Schema 以该草稿为准；`DamageReport` 的版本、人工复核和 provenance 由本地代码构造。相比在收到完整模型对象后覆盖字段，这一方式从契约上消除模型伪造生成时间或人工复核事实的可能。

### 2. 固定内部等级枚举

内部等级使用 `undetermined/low/medium/high/critical`。Pydantic 在读取人工编辑或兼容数据时接受常见中文别名并规范化，AI 严格 Schema 只暴露规范值。显示层负责中文标签。分块总体等级只基于规范值计算。

### 3. 证据身份集合为不可变主键

输入身份为有序 `(image_name, finding_index)` 列表。AI 允许重排和重新表述 `damage_type`，但返回集合必须无遗漏、无新增、无重复；校验成功后按输入顺序重排。任何不一致均作为生成错误进入不判级本地兜底，并在完整性状态中记录，不能被静默确认。

### 4. 人工确认执行二次完整性校验

保存人工修改和确认共用本地校验。确认额外要求：报告版本为 v3、证据身份与 evidence snapshot 一致、所有损伤等级已确定、复核人非空且不是占位文本。确认时间由本地 UTC 时间写入。施工方案继续只读取持久化报告，并同时检查 v3、`confirmed_by_human` 和完整性状态。

### 5. 视觉附件预算在网络请求前确定

仅附加含报告 finding 的成功图像；每张图最多附加原图和识别覆盖图。使用 Pillow 自动应用 EXIF 方向、转 RGB、移除元数据、按最长边缩放并编码 JPEG。固定最大图片数、最大单图编码字节数和最大总字节数；无法满足预算时生成明确错误并走保守兜底。生成审计记录附件角色、原始尺寸/字节数、发送尺寸/字节数及是否缩放，不记录 Base64 内容。

### 6. 保留主线流式与 RAG 契约

`ResponsesReportService` 继续使用 `on_text_update` 累计全文回调。GUI 的现有“当前文件”预览无需改成 delta 拼接。知识检索继续从 `pipeline_search_with_scope` 进入，`GenerationContext` 中 anchors、context groups、warnings、source mode 和 route diagnostics 继续写入 manifest 和提示词。

### 7. 下游数据使用可空尺度字段

修复计划和施工方案保留字段名兼容，但 `component_area_ratio`、`physical_area_mm2` 等尺度数据在无人工量测时为 `null`。DOCX 映射显示“不适用（无尺度换算）”。不再从检测掩膜推导数量依据或施工范围。

### 8. 旧报告只读兼容

读取端可以识别 v1 包络并显示，但不能把它直接改写为 confirmed v3，也不能据此生成施工方案。迁移通过重新生成 v3 或显式的受测转换函数完成；本变更优先实现重新生成提示和门控，不做静默字段猜测。

### 9. 源码内聚与旧链路退役

`分析报告生成` 目录仅用于本次人工对照，主项目不得增加指向该目录的 import、文件读取、配置项、环境变量或启动时 fallback。所需行为在主项目模块中重新实现并适配现有架构。v3 通过聚焦和全量回归后，删除 v1 专用几何输入模型、旧报告 Schema 输出、根据面积/规则等级生成本地报告的逻辑，以及无需人工确认即可继续后续流程的分支；仅保留版本识别和拒绝旧报告下游使用的最小兼容代码。

## Risks / Trade-offs

- [视觉附件重编码可能损失细节] -> 使用确定的最长边和质量下限，审计实际尺寸；超预算时失败而不是继续强压缩。
- [严格证据对应会增加远程失败率] -> 提示词明确身份不可变，失败时保留不判级报告和可操作错误，避免错误报告进入下游。
- [新增实名复核增加操作步骤] -> 复核人作为紧凑输入放在现有报告区，不增加独立页面。
- [v3 对旧消费者是破坏性升级] -> 同步修改施工方案、DOCX、GUI 和测试；旧 v1 只读，不覆盖原文件。
- [图片和层级知识上下文增加请求量] -> 视觉预算和既有知识上下文上限共同约束请求。

## Migration Plan

1. 先落地 v3 Schema、草稿构造、身份校验和视觉附件预算的单元测试。
2. 在保持 `pipeline_search_with_scope` 和累计式回调的前提下接入报告服务。
3. 接入 GUI 最小检测摘要、人工编辑/实名确认和下游门控。
4. 同步修复计划、施工方案、DOCX 映射和生成清单。
5. v3 聚焦测试通过后删除被替代的 v1/几何报告生成代码和旧工作流分支，再运行一次禁止跨目录引用的静态检查。
6. 运行完整测试、严格 OpenSpec 校验和 offscreen GUI smoke。
7. 以当前主线文件作为回滚点；若 GUI 或下游回归，回退本变更涉及文件，不切换 active RAG 数据库。

## Open Questions

- 真实供应商对多图请求的硬限制需要通过一次受控在线 smoke 验证；本地预算采用更保守的应用限制。
- DOCX 最终视觉排版仍需人工打开成品复核，自动测试只验证结构和占位符替换。
