## Context

当前自动流程已把报告和施工方案生成拆到后台线程，并在两个阶段之间设置人工审核门禁。主按钮却在 `AutomaticWorkflowWorker` 返回“等待报告审核”以及 `ConstructionPlanWorker` 返回“等待施工方案审核”时恢复为“启动”，导致同一次流程在尚未结束时呈现空闲状态。

施工方案确认后，GUI 通过零延迟计时器调用 `render_repairs()`。该方法最终在 GUI 主线程同步执行 `FhlRepairRenderer.render_many()`；每个渲染项包含外部进程和网络等待，事件循环无法处理重绘或输入，因此窗口会显示“未响应”，用户也看不到已经切换到渲染阶段。

现有渲染器已经支持 `should_stop` 和 `on_result` 回调，并为每项写入可恢复的渲染清单。实现应复用这些能力，不改变 FHL 请求、结果模型或工程审核门禁。

## Goals / Non-Goals

**Goals:**

- 在识别、报告审核、施工方案生成、施工方案审核和可选渲染之间保持一致的“停止”运行态。
- 在不支持安全取消的生成或审核等待阶段禁用主按钮，在后台渲染阶段启用主按钮以停止剩余渲染项。
- 让修复渲染不阻塞 Qt GUI 线程，并实时显示阶段与逐项结果。
- 只在完成、取消或失败等终态恢复“启动”。
- 所有支持窗口尺寸都显示完整的“生成修复渲染图”。

**Non-Goals:**

- 不让报告或施工方案远程生成线程支持强制中断。
- 不终止已经启动的单个 FHL 子进程；停止请求在当前项结束后阻止后续项启动。
- 不改变 `hold`、`evidence_inconsistent`、`construction_released` 或人工审核的工程含义。
- 不调用真实外部 API 进行自动化测试。

## Decisions

### 引入专用修复渲染工作线程

增加轻量 `RepairRenderWorker(QThread)`。工作线程接收渲染项、输出目录、API 配置和提示词，在 `run()` 内构造 `FhlRepairRenderer` 并调用 `render_many()`。`on_result` 通过 Qt 信号发送逐项结果，完成、取消和异常分别发送独立信号。

在工作线程内构造渲染器，避免把带可变清单状态的服务对象跨线程使用。相比继续用 `QTimer.singleShot()`，真实线程能保证 GUI 事件循环在外部进程和网络调用期间继续运行。

### 将主按钮状态按工作流终态管理

沿用已有 `_set_primary_button_running()` 作为运行态唯一入口，并补充统一的空闲态恢复方法。报告或施工方案等待审核时调用运行态方法且禁用按钮；渲染线程启动时保持“停止”并启用按钮；无渲染选择、阻断状态、无可渲染项、渲染完成、渲染取消或失败时进入空闲态。

不使用“当前是否有线程运行”单独判断整个流程，因为人工审核期间没有后台线程但业务流程仍未结束。按钮状态由生命周期回调显式推进。

### 渲染停止只取消剩余项

主按钮的运行检测加入 `render_worker`。渲染阶段点击“停止”时只设置工作线程的停止标志并保持按钮为禁用“停止”，直到当前项返回、剩余项被记录为取消且线程发出终态信号。这样不会在后台仍运行时错误显示“启动”。

### 完整文案不再响应式缩写

`render_checkbox` 在所有视口都使用“生成修复渲染图”。紧凑布局通过既有最小宽度和字体缩放容纳文字，不再删除末尾“图”字；工具提示保持相同文案。

## Risks / Trade-offs

- [当前 FHL 项不能立即强制终止] -> 按钮和状态明确显示正在停止，当前项结束后取消剩余项；避免直接杀进程造成输出或清单损坏。
- [工作线程结束顺序与 Qt 信号排队存在短窗口] -> 终态槽负责恢复按钮，`finished` 槽只清理线程引用，不重复改变业务状态。
- [审核窗口关闭但未确认时按钮保持“停止”可能被理解为后台仍在计算] -> 状态区继续明确显示“等待人工审核”，主按钮禁用，防止启动另一批任务覆盖当前上下文。
- [窄窗口完整文案可能增加最小宽度] -> 保留现有紧凑尺寸测试，并检查 `sizeHint()` 不超过控件宽度。

## Migration Plan

1. 增加生命周期与后台渲染的失败回归测试。
2. 引入渲染工作线程和终态回调，迁移 `render_repairs()` 的同步执行。
3. 调整报告审核、施工方案审核和渲染各分支的主按钮状态。
4. 统一渲染选项文字，执行聚焦、完整、OpenSpec 和离屏界面验证。

无需数据迁移。回滚仅涉及 GUI 调度与测试，已有报告、施工方案和渲染清单仍兼容。

## Open Questions

无。现有渲染器的逐项停止合同足以支持本次后台化。
