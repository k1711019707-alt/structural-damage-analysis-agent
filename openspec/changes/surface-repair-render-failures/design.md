## Context

`FhlRepairRenderer.render_one()` 通过 Node 插件调用 FHL Images API。当前非零返回码统一转换为“FHL Images API 未成功回传”，丢弃了已经捕获的 stdout 和 stderr。`RepairRenderWorker` 会正常返回包含失败结果的列表，因此 GUI 的 `on_render_worker_completed()` 无条件将批次标记为“流程完成”。

实际运行证据是 5/5 项失败、`output_path=null`，实时单图诊断显示插件经过 3 次重试后仍返回 `HTTP 502 Bad gateway`。正确输出目录存在且可写，`render_manifest.json` 已正常落盘；缺失的是上游生成的图片。

## Goals / Non-Goals

**Goals:**

- 保存足以定位上游失败类型的简短诊断，同时防止 API Key 进入清单或 GUI。
- 依据结果状态准确区分全部成功、部分失败、全部失败和取消。
- 在 GUI 和事件日志中明确没有生成图片、失败数量、首个失败原因和输出目录。
- 保留成功图片和现有可恢复清单。

**Non-Goals:**

- 不改变 FHL 插件的重试、路由或接口协议。
- 不把其他图像服务作为自动回退。
- 不把失败记录伪装成图片文件。
- 不保证 FHL 上游在本次修改后恢复可用。

## Decisions

### 从子进程输出提取稳定摘要

非零返回时合并 stderr 与 stdout，优先选择包含 `Edit failed:`、`HTTP`、`ERROR` 或 `FAILED` 的末尾诊断行，去除重复空白并限制长度。摘要会替换当前 API Key；如果没有可用文本，则保留现有泛化消息并附返回码。

相比把完整插件日志写入清单，短摘要可以保留 HTTP 状态和服务消息，同时避免清单膨胀或无意泄露运行环境。原始完整日志仍可在人工诊断命令中观察。

### 根据结果计数决定 GUI 终态

`success` 和 `resumed` 计为已生成/可用；`failed` 计为失败；`cancelled` 计为取消。全部失败时进入“修复渲染失败”终态，不记录“全部阶段已结束”；部分失败时进入“流程部分完成”，并保留成功结果；没有失败时才进入正常完成。

工作线程本身抛出异常仍使用已有 `on_render_worker_failed()`。单项服务失败是结构化业务结果，由完成槽聚合，不升级为线程崩溃。

### 逐项失败进入用户级日志

收到失败项时记录来源文件名和脱敏后的简短原因。批次开始日志增加实际输出目录，批次结束日志记录成功、恢复、失败、取消计数。这样无需打开 JSON 清单即可从 GUI 判断是否真的产生了图片。

## Risks / Trade-offs

- [上游消息包含敏感内容] -> 显式替换 API Key、截断长度，只选单行摘要。
- [插件未来改变错误格式] -> 关键词选择失败时回退到最后一个非空行和返回码。
- [部分失败被误认为全部可用] -> 使用“部分完成”而不是“完成”，并显示精确计数。
- [进度 100% 被理解为成功] -> 进度表示批次已结束；状态面板明确显示失败终态和零张落盘。

## Migration Plan

无需迁移。新失败会写入更具体的 `message`；旧 `render_manifest.json` 仍可读取。回滚只恢复消息和 GUI 汇总逻辑，不影响已生成图片。

## Open Questions

无。当前上游 502 属于外部服务可用性问题，待服务恢复后重新运行即可由现有恢复逻辑跳过成功项。
